# BhuVistaar — Judge Technical FAQ

This document provides rigorous, code-grounded answers to technical and architectural questions commonly posed by hackathon judges and evaluation panels.

---

### 1. Why not just use 2D GIS?
**Answer:** A 2D GIS represents land rights as flat polygons on a single planar surface. In multi-storey buildings, commercial complexes, and subterranean spaces, multiple distinct property units occupy the exact same 2D footprint. Collapsing them into 2D creates spatial ambiguity, destroys vertical boundary semantics, and makes it impossible to detect multi-owner vertical overlaps or air-rights infringements.

### 2. Why 3D?
**Answer:** Vertically separated property strata require explicit vertical extents $[z_{\text{min}}, z_{\text{max}}]$ defined in metric coordinates above Mean Sea Level (MSL). Explicit 3D volumes allow spatial engines to mathematically calculate vertical non-overlap, building height compliance, and subterranean easements without data loss.

### 3. Why VUID (Volumetric Unique Identifier)?
**Answer:** To provide an immutable, deterministic primary key for every 3D spatial unit revision. The VUID is generated by hashing the canonical WKB representation of the unit's 2D footprint combined with its normalized vertical intervals.

### 4. Why not an official 3D ULPIN?
**Answer:** The Government of India's 14-digit ULPIN (Bhu-Aadhaar) is an authoritative national standard for 2D land parcels. The Ministry of Rural Development has not yet enacted a formal statutory standard for 3D ULPIN numbering. Claiming to mint official 3D ULPINs would be legally false. Therefore, BhuVistaar uses "Prototype VUID" and maintains prominent disclaimers across all outputs.

### 5. Why machine assistance (AI)?
**Answer:** Manual drafting of 3D cadastre from diverse architectural floorplans, LandXML files, and survey sketches is slow and labor-intensive. Heuristic and machine learning models assist human surveyors by proposing initial 3D prisms, inferring floor boundaries, and flagging anomalies.

### 6. Why isn't AI authoritative?
**Answer:** Machine learning models have non-zero error rates, produce hallucinations, and lack statutory authority. A land administration system cannot tolerate stochastic boundary decisions. In BhuVistaar, AI proposals are strictly non-authoritative: they must pass independent deterministic spatial validation and receive explicit human officer sign-off before entering any governance state.

### 7. How is geometry deterministically validated?
**Answer:** Gate A validation executes strict mathematical rules using Shapely 2.0 and PostGIS relational spatial functions. Rules check:
- `GEO-001..004`: Coordinate validity, 2D ring closure, non-self-intersection, and positive height ($z_{\text{max}} > z_{\text{min}}$).
- `TOP-001`: Ground footprint must be strictly contained within the parent parcel boundary (`ST_Contains`).
- `VRT-003`: Stacked floor units must not overlap vertically ($z_{\text{max}}(L01) \le z_{\text{min}}(L02) + \epsilon$, with tolerance $\epsilon = -0.001\text{m}$).

### 8. What is VRT-003?
**Answer:** Rule `VRT-003` is the vertical stratification non-overlap rule. In our flagship demonstration scenario, Level L01 ceiling is set to 106.50m while Level L02 floor is set to 106.00m. The rule detects an illegal 0.50m physical overlap and emits an immovable BLOCKER issue.

### 9. What happens when evidence conflicts?
**Answer:** If two evidence files disagree (e.g. Total Station survey reports floor at 106.0m while an architectural drawing reports 106.5m), BhuVistaar does not silently choose one. It flags an `EVIDENCE_CONFLICT` anomaly, presents both sources in the Side-by-Side Evidence Triad, and requires explicit human officer resolution.

### 10. What happens when AI is wrong?
**Answer:** If AI proposes an invalid candidate (e.g. high confidence but overlapping geometry), our Disagreement Engine records **Case A (`AI_VALIDATION_DISAGREEMENT`)**. Gate A emits a BLOCKER, and Gate C strictly prevents approval. The candidate cannot advance until corrected by a human officer.

### 11. What happens when evidence changes?
**Answer:** BhuVistaar tracks SHA-256 checksums of all evidence files. If an underlying evidence file is updated or replaced, the system marks all dependent candidates as `STALE_EVIDENCE`, invalidates their validation status, and demands reprocessing.

### 12. How are revisions preserved?
**Answer:** BhuVistaar uses a non-destructive revision model. When an officer corrects a defect, the system never overwrites the database row. It creates Revision 2 (`predecessor_revision_id = Rev 1`), recalculates a new deterministic VUID, and preserves Revision 1 intact for legal auditing.

### 13. How is provenance tracked?
**Answer:** Every spatial unit revision is linked to a `provenance_records` row, which stores the IDs, filenames, and SHA-256 digests of all source evidence used during its creation.

### 14. How is stale validation prevented?
**Answer:** The `ApprovalService` compares the timestamp of the latest validation run against the creation timestamp of the revision. If the revision was modified after the validation run, Gate C flags `VALIDATION_OUTDATED` and blocks approval until revalidation is executed.

### 15. How is reproducibility achieved?
**Answer:** The `ReproducibilityService` computes a unified SHA-256 snapshot hash over the input evidence checksums, canonical geometry WKB, coordinate reference system, model configuration, ruleset version (`v1.0.0`), and git commit hash. Re-running the golden workflow yields identical state.

### 16. How does interoperability work?
**Answer:** BhuVistaar exports data in three open standards:
1. `BhuVistaar JSON v1.0.0`: Full schema with provenance, revisions, and audit trails.
2. `2D GeoJSON (RFC 7946)`: Standard FeatureCollection with vertical properties for GIS tools like QGIS.
3. `3D Wavefront OBJ`: Volumetric polygon mesh for 3D CAD/BIM tools like Blender or AutoCAD.
Round-trip integrity is verified via `POST /api/v1/export/roundtrip/verify`.

### 17. What is synthetic?
**Answer:** The demo parcel (`ULPIN 12345678901234`), 4 floor units, Total Station GeoJSON, and architectural plans are synthetic fixtures modeled in UTM Zone 43N. They are labeled `SYNTHETIC PROTOTYPE DATA` across all screens.

### 18. What is actually benchmarked?
**Answer:** The automated evaluation harness benchmarks candidate generation and anomaly detection models across 10 controlled synthetic scenarios. Results are clearly marked `SYNTHETIC PROTOTYPE EVALUATION` and do not claim real-world field statistics.

### 19. What is production-ready?
**Answer:** The Docker Compose orchestration, PostgreSQL 16 + PostGIS 3.4 persistence layer, Alembic migrations, tri-level health checks, deterministic validation rules, non-destructive revisioning, and append-only audit trails are verified engineering components.

### 20. What remains to be built?
**Answer:** Transitioning to production requires: statutory legislation recognizing 3D cadastral rights, official 3D ULPIN standard formulation, Class 3 DSC/Aadhaar PKI digital signatures, real-time API sync with state land registries (Bhoomi, Dharani), and IndexedDB persistent offline field storage.
